# QAVEN — خطة ربط المصادقة والخدمات الخلفية

> هذه الوثيقة ناتج مرحلة "الواجهة أولاً". كل ما يلي **لم يُربط بعد** —
> الواجهة جاهزة ومكتملة الحالات، والنقاط المعلّمة `TODO(AUTH)` في الكود
> هي نقاط الربط بالضبط.

---

## 1. الوضع الحالي

| المكوّن | الحالة |
|---|---|
| `/login` — تصميم مقسوم Premium + كل الحالات | ✅ جاهز |
| تدفق دخول: حساب → كلمة مرور → OTP | ✅ واجهة كاملة |
| تدفق تسجيل: بيانات → OTP | ✅ واجهة كاملة |
| زر Google (بدون ربط) | ✅ واجهة + حالة "قيد الاتصال" |
| حالات خطأ/تحميل/نجاح + أنيميشن | ✅ جاهزة |
| Checkout للضيوف (بدون بوابة دخول) | ✅ يعمل فعلياً |
| المصادقة الحقيقية | ⏳ لم يُربط |
| قاعدة البيانات | ⏳ لم تُربط |

**مبدأ التصميم:** لا بيانات وهمية — أزرار الدخول تعرض الحالة الصحيحة
(تحميل ثم رسالة "سيُفعّل عند ربط المصادقة") بدلاً من أن تعمل بشكل مزيف.

---

## 2. الخدمات المطلوب ربطها

### أ) المصادقة

| الخدمة | الغرض | التوصية |
|---|---|---|
| Google OAuth | زر "المتابعة باستخدام Google" | **Supabase Auth** أو Firebase Auth أو NextAuth (Auth.js) |
| Email + Password | دخول بالبريد | نفس المزوّد |
| Phone + OTP | دخول/تسجيل برقم عُماني + رمز SMS | Supabase (SMS عبر Twilio/Vonage) أو Firebase Phone Auth |
| الجلسات (Sessions) | حفظ دخول العميل بين الزيارات | HttpOnly cookies عبر Next.js Route Handlers |

> عملياً: مزوّد واحد (مثل Supabase Auth) يغطي الأربعة — لا حاجة لأربع خدمات منفصلة.

### ب) قاعدة البيانات (تخزين)

| البيانات | الجداول المقترحة (موجودة في `src/lib/db/schema.ts`) |
|---|---|
| العملاء | `customers` |
| العناوين | `addresses` |
| الطلبات | `orders` + `order_items` |
| إيصالات التحويل البنكي | `bank_transfer_receipts` (رفع الملف إلى Storage) |
| المنتجات/التصنيفات/المخزون | `products`, `categories`, `inventory`, … |
| طرق التوصيل والدفع | `delivery_methods`, `payment_methods`, `settings` |

**التوصية:** PostgreSQL مُدار (Supabase / Neon / PlanetScale-style). مخطط SQL
الكامل موثق في `docs/DATABASE.md`.

### ج) خدمات مساندة

| الخدمة | الغرض |
|---|---|
| Object Storage (S3/Supabase Storage) | صور إيصالات التحويل + صور المنتجات مستقبلاً |
| SMS Provider | إرسال OTP للأرقام العُمانية (Twilio / Vonage / Unifonic) |
| Email Provider | إيميلات تأكيد الطلب والاسترجاع (Resend / SendGrid) — اختياري الآن |

## 3. من يجهّز ماذا؟

### أنت تجهّز:

1. **حساب مزوّد مصادقة** — إنشاء مشروع Supabase (أو Firebase) وتزويدي بـ:
   - Project URL + anon key (توضع في `.env.local`)
   - تفعيل مزوّد Google (Client ID + Secret من Google Cloud Console)
   - تفعيل Phone Auth + ربط حساب Twilio/Vonage برصيد SMS
2. **قاعدة بيانات** — إنشاء PostgreSQL وتزويدي بـ connection string
3. **حساب SMS** — لو اخترت مزوّداً منفصلاً عن قاعدة البيانات
4. **قرار تجاري:** هل OTP مطلوب في **كل** دخول، أم فقط عند تسجيل جهاز جديد؟
   (التجربة الحالية تفترض "كل دخول" — قابلة للتبسيط لاحقاً)

### أنفّذ أنا داخل المشروع عند الربط:

1. تثبيت مكتبة المزوّد وضبط `.env.local`
2. إنشاء `src/app/api/auth/*` (Route Handlers):
   - `/api/auth/google` — بدء OAuth + callback
   - `/api/auth/login`, `/api/auth/register`, `/api/auth/verify-otp`
   - `/api/auth/resend-otp`, `/api/auth/logout`
3. استبدال كل `TODO(AUTH)` في `src/components/auth-experience.tsx` بالنداءات
   الحقيقية (نفس أسماء الحالات — صفر تغيير في الواجهة)
4. ربط `AuthProvider` بالجلسة الحقيقية (جلب العميل من الجلسة)
5. تهيئة جداول قاعدة البيانات من `docs/DATABASE.md` (SQL جاهز للتنفيذ)
6. رفع الإيصالات إلى Storage وتخزين روابطها في `bank_transfer_receipts`
7. تحويل الطلبات من مرآة الجلسة إلى `POST /api/orders`
8. اختبار التدفق كاملاً: Google / بريد / هاتف + OTP / طلب مع إيصال

---

## 4. ترتيب الربط المقترح (عندما تقرر)

1. قاعدة البيانات + جداول العملاء والعناوين والطلبات
2. Email/Password + Google (الأسرع اختباراً)
3. Phone + OTP عبر SMS
4. ربط Checkout بجلب العنوان المحفوظ تلقائياً
5. لوحة إدارة الطلبات لاحقاً

---

## 5. ملاحظات أمنية (سأطبقها عند الربط)

- تحقق OTP على الخادم فقط — الواجهة لا تقرر الصحة أبداً
- جلسات HttpOnly cookies (غير مقروءة من JS) بدل التخزين المحلي
- Rate-limiting على إرسال OTP (حد أقصى / رقم / ساعة)
- رفع الإيصالات عبر رابط موقّع فقط، بحد حجم ونوع ملف
- لا تُخزن كلمات المرور أبداً في المشروع — المزوّد يتكفل بالتجزئة
